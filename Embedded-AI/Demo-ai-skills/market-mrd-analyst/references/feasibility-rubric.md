# 可行性评分准则

## 技术可行性

从 1-5 分评估，必要时给出区间：

- 5：核心技术成熟，团队已有能力，MVP 可快速验证。
- 4：技术路径明确，有少量集成或数据挑战。
- 3：可实现，但依赖关键数据、模型、硬件、供应链或复杂系统集成。
- 2：存在重大技术未知，需要原型验证后才能判断。
- 1：当前约束下不可行或成本极高。

检查维度：

- 核心技术是否成熟
- 是否依赖难获取数据
- 是否依赖硬件、供应链、认证或现场部署
- 是否存在实时性、可靠性、安全性或合规要求
- MVP 是否能用较小范围验证
- 团队能力是否匹配

### 硬件/消费电子评分补充

硬件产品不能只按"技术上能不能做"评分。必须把团队能力、量产、供应链、认证和售后纳入技术可行性。

缺少团队能力、供应链、样机、认证路径证据时：

- 普通硬件/消费电子：技术可行性默认不得高于 3/5。
- 涉及无线、音频/图像算法、医疗/安全、精密测量、强实时、量产一致性：团队能力未知时默认不得高于 2/5。
- 已有成熟方案商、核心器件供应、样机或团队经验时，才可提高评分，并写清证据来源。

必须检查：

- 核心器件和供应链成熟度。
- 固件/算法/射频/结构/工业设计/测试能力。
- 量产良率、一致性、校准、老化、可靠性。
- 认证、安规、EMC、无线、电池、环保。
- 维修、退换货、售后和质保成本。
- App/云服务/账号/数据安全依赖。

## 商业可行性

从 1-5 分评估：

- 5：痛点强、预算明确、渠道清晰、销售周期可控、毛利空间合理。
- 4：需求明确，但获客或交付仍需验证。
- 3：有机会，但付费意愿、渠道或单位经济模型不清晰。
- 2：用户价值不够强或商业路径重度依赖假设。
- 1：难以形成可持续商业模式。

检查维度：

- 用户是否有明确预算
- 购买者和使用者是否一致
- 采购/决策链是否复杂
- 定价是否能覆盖交付和获客成本
- 毛利是否被硬件、实施、服务或渠道分成吞噬
- 是否有复购、订阅、耗材、数据或生态收益

## 综合建议（量化门槛）

记技术可行性为 T（1-5），商业可行性为 B（1-5），痛点强度证据为 P（弱 / 中 / 强）。

- **Go**：T ≥ 4 且 B ≥ 4 且 P ≥ 中。所有关键假设已有证据支持。
- **No-Go**：T ≤ 2 或 B ≤ 2 或 P = 弱（用户其实没那么在意）。或存在无清晰验证路径的致命风险。
- **Explore**：其余情况。早期想法默认偏向 Explore。

额外规则：

- 多数早期想法（clarity < 90）即使 T、B 都高也应给 `Explore`，因为 `Value` 和 `Viability` 假设还没验证。
- 给 `Go` 时必须列出"还剩哪些假设未验证"，给 `No-Go` 时必须列出"什么条件下可以重新评估"。
- 严禁为了迎合用户想法强行 `Go`。如果数据指向 No-Go 或 Explore，直接说。

## 评分常见误判

- 不要因为"听起来有市场"就给 T 或 B 高分。必须有具体证据（用户访谈、竞品收入、试点反馈等）。
- "技术上可以做"不等于 T ≥ 4。如果团队没有相关经验、依赖未获取的数据或供应链，T 应 ≤ 3。
- "用户应该会买"不算 P ≥ 中。需要访谈、问卷、付费测试等行为证据。
