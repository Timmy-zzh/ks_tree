# 调试不是猜谜游戏

面对一个偶现故障，最危险的做法是立刻修改最可疑的代码。改动也许让现象消失，却可能没有触及根因，还破坏了原本可以复现问题的现场。

## 从事实开始

先把“知道”和“猜测”分开。一个好的问题描述至少包括：

- 观察到了什么，而不是认为发生了什么
- 第一次出现的版本与时间
- 出现概率和必要条件
- 已经排除的因素及其证据

例如，“设备偶尔卡死”不是可行动的问题；“固件 2.3.1 在弱网重连时，约 3% 概率停止喂狗，最后一条日志来自 MQTT 回调”就清晰得多。

## 建立时间线

嵌入式系统的问题经常跨越中断、任务和外设。为日志提供统一时间戳与事件编号，可以把离散线索重新拼成因果链。

```c
#define TRACE_EVENT(id, value) \
    trace_write(monotonic_us(), (id), (uint32_t)(value))

void network_reconnect(void) {
    TRACE_EVENT(EVENT_RECONNECT_BEGIN, retry_count);
    /* reconnect steps */
    TRACE_EVENT(EVENT_RECONNECT_END, result);
}
```

日志的目标不是越多越好，而是在不显著改变系统时序的前提下，记录关键状态变化。

## 每次只改变一个变量

如果同时改超时、栈大小和任务优先级，即使问题消失，也无法知道哪个变化真正有效。使用最小实验：提出一个假设，只调整一个变量，记录结果，再决定下一步。

> 调试的速度，取决于排除假设的速度，而不是修改代码的速度。

## 修复之后

修复并不以“问题不再出现”为终点。还需要补上自动化用例、故障注入或运行时断言，让同一类错误以后更早暴露。

一次故障如果只留下一个补丁，它的价值很有限；如果还能留下更好的可观测性与防护机制，它才真正提升了系统质量。
