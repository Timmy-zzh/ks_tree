# 从实验指标回到真实世界

在开发板上跑通一个模型令人兴奋。但当它进入真实产品，问题很快会从“准确率是多少”变成：设备能否连续运行？峰值内存是否可控？异常后能否自恢复？

> Demo 证明一件事可以发生，产品则要证明它可以持续发生。

## 先定义系统预算

边缘设备的每一种资源都有限。开始优化前，我会先写下一份明确的预算：

| 维度 | 目标 | 测量方式 |
| --- | --- | --- |
| 端到端时延 | P95 小于 80 ms | 连续记录 24 小时 |
| 峰值内存 | 小于 256 MB | 进程与系统双重采样 |
| 平均功耗 | 小于 5 W | 典型场景功耗仪测量 |
| 异常恢复 | 30 秒内恢复 | 故障注入测试 |

预算的价值在于让讨论从“应该更快”变成“还差 12 ms”。这会直接影响模型选择、预处理位置，以及任务如何并行。

## 测量完整链路

只测推理时间通常会漏掉真正的瓶颈。一个常见链路包含：

1. 传感器采集与数据搬运
2. 解码和预处理
3. 模型推理
4. 后处理与业务决策
5. 结果上传或界面渲染

可以用统一的单调时钟给各阶段埋点：

```c
typedef struct {
    uint64_t capture_us;
    uint64_t preprocess_us;
    uint64_t inference_us;
    uint64_t postprocess_us;
} pipeline_metrics_t;

static inline uint64_t elapsed_us(uint64_t begin, uint64_t end) {
    return end >= begin ? end - begin : 0;
}
```

不要只看平均值。P95、P99 和最坏情况，才更接近用户真正感受到的体验。

## 把异常当作正常路径

摄像头会掉线，模型文件会损坏，内存申请也可能失败。可靠的系统不会假设这些事情不发生，而是明确每类异常的状态转移：重试、降级、重启模块，还是让 watchdog 接管。

这里有三个实用原则：

- 为每个外部依赖设置超时，不做无限等待。
- 区分可恢复错误与致命错误，避免“一错就重启”。
- 保存足够少但足够关键的现场信息，支持事后定位。

## 最后的检查清单

模型压缩与算子优化固然重要，但产品化是一项系统工程。上线前，我至少会确认：资源预算有数据支撑、长稳测试覆盖关键场景、升级能回滚、日志不会拖垮存储，以及无网络时核心能力依旧可用。

当这些问题都有清楚答案时，模型才真正从实验室走进了产品。
