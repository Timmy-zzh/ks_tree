# 任务划分决定了系统的形状

RTOS 提供了任务、队列、信号量等工具，但工具不会自动带来清晰的架构。任务划分不当，系统很快会充满共享状态、隐式依赖和难以解释的时序问题。

## 开始前的七个问题

在创建一个新任务之前，我会先回答：

1. 它拥有哪一类资源或状态？
2. 它由事件驱动，还是需要固定周期？
3. 最坏执行时间是多少？
4. 它可以阻塞多久？
5. 谁向它发送数据，它又影响谁？
6. 失败后能否独立恢复？
7. 这个职责是否真的需要独立并发？

最后一个问题尤其重要。很多“任务”其实只是一个普通模块或状态机，为它创建线程只会增加上下文切换和同步成本。

## 用消息传递所有权

比起让多个任务直接修改同一份数据，我更倾向于定义明确的消息，让某个任务拥有状态。

```c
typedef enum {
    SENSOR_SAMPLE_READY,
    SENSOR_RECONFIGURE,
    SENSOR_SHUTDOWN
} sensor_event_type_t;

typedef struct {
    sensor_event_type_t type;
    uint32_t timestamp_ms;
    union {
        float sample;
        sensor_config_t config;
    } data;
} sensor_event_t;
```

这样做让写入点更少，状态变化更容易追踪，也能自然形成模块边界。

## 优先级不是重要性排名

任务优先级应该由响应时间、截止期限和阻塞关系决定，而不是业务名称听起来有多重要。过多高优先级任务可能让低优先级任务长期得不到运行，还会放大优先级反转的风险。

先用简单、保守的优先级层级运行起来，再根据真实测量调整，通常比一开始精细设计十几个级别更可靠。

## 给系统留下余量

CPU 利用率长期接近 100%，不代表资源使用充分，而代表系统没有空间处理峰值和异常。栈、队列深度也同样需要基于高水位测量保留合理余量。

好的 RTOS 设计不是任务数量多，而是每个任务的责任和边界都容易说清楚。
