## 2. 先建立一个整体认识

### 2.1 ZeroMQ 是什么

ZeroMQ（通常写作 ØMQ 或 ZMQ）是一个嵌入应用进程中的异步消息通信库。它提供 Socket、消息队列、连接管理和多种通信模式，但默认不会启动一个独立的消息服务器。

可以把它理解为：

```text
你的业务进程
+--------------------------------------------------+
| 业务代码                                         |
|   创建 Context、Socket，发送和接收消息            |
|                                                  |
| libzmq                                            |
|   队列、连接、I/O 线程、协议和传输实现            |
+--------------------------------------------------+
        |                 |                 |
     tcp://            ipc://           inproc://
```

因此，使用 ZeroMQ 时通常不需要先安装一个像 Kafka Broker 或 RabbitMQ Server 那样的中心服务。通信双方的队列和连接逻辑主要存在于各自进程中。

这并不意味着 ZeroMQ 自动提供以下能力：

- 默认磁盘持久化；
- 默认消息落盘和崩溃恢复；
- 默认集群协调；
- 默认业务级重试、幂等和事务；
- 默认身份认证和授权。

这些能力需要通过应用设计、Socket 选项、代理程序或其他系统补充。后续周次会继续学习可靠性、安全和生产化设计。

### 2.2 与传统 TCP Socket 的区别

| 方面 | 原始 TCP Socket | ZeroMQ Socket |
| --- | --- | --- |
| 数据抽象 | 字节流，需要自行处理分包和粘包 | 消息，保留消息边界 |
| 连接管理 | 应用自行处理连接、重连、队列 | libzmq 负责大量底层连接管理 |
| 通信模式 | 通常自己设计请求、响应和广播 | 使用 REQ/REP、PUB/SUB 等模式 |
| 缓冲和排队 | 主要依赖内核缓冲区和自建队列 | 提供进程内消息队列和高水位机制 |
| 多路复用 | 需要自行使用 `select`、`poll` 或线程 | 可使用 ZeroMQ Socket 和 `poll` 等机制 |
| 约束 | 规则少，但需要自己实现更多内容 | 规则更多，但可以减少样板代码 |

ZeroMQ 不是“更快的 TCP API”这么简单。它在 TCP 之上增加了消息抽象、模式约束和队列机制；同时也要求使用者理解 Socket 类型、发送接收状态和生命周期。

### 2.3 与 Kafka、RabbitMQ 的区别

这里比较的是典型使用方式，不代表所有产品配置都完全相同：

| 方面 | ZeroMQ | Kafka | RabbitMQ |
| --- | --- | --- | --- |
| 主要形态 | 嵌入应用的通信库 | 独立运行的分布式日志系统 | 独立运行的消息代理 |
| 是否需要中心服务 | 通常不需要 | 需要 Broker 集群 | 需要 Broker |
| 持久化 | 默认不提供磁盘消息持久化 | 核心能力之一 | 可配置持久化 |
| 编程模型 | Socket 模式和拓扑 | Topic、Partition、Consumer Group | Exchange、Queue、Binding |
| 典型优势 | 低开销、灵活、适合进程间通信 | 吞吐、日志保留、消费位点 | 路由、确认、管理能力 |
| 需要自行设计的部分 | 可靠性、拓扑和业务语义 | 相对较少 | 相对较少 |

选择 ZeroMQ 时，通常是希望把通信能力嵌入服务，而不是引入一个必须单独运维的消息中间件。

## 3. 关键组件和分层关系

### 3.1 libzmq、cppzmq、ZMTP 的关系

```text
应用代码（C++）
       |
       v
cppzmq：C++ header-only 封装，提供 zmq::context_t 等类型
       |
       v
libzmq：ZeroMQ 的核心 C/C++ 实现，提供队列、Socket、I/O 和传输
       |
       v
ZMTP：ZeroMQ Message Transport Protocol，负责网络消息传输协议
       |
       v
TCP / IPC / 内存中的进程内传输
```

- **libzmq**：真正执行 ZeroMQ 核心逻辑的库。本项目使用的是 `cmake_libzmq` 中的头文件和库文件。
- **cppzmq**：C++ 绑定，主要由 `zmq.hpp` 和可选的 `zmq_addon.hpp` 提供。它是 header-only，但仍然需要链接 libzmq。
- **ZMTP**：ZeroMQ 的消息传输协议。学习它有助于理解网络连接和消息帧，但本周只需要知道它位于 libzmq 的传输实现层。

“cppzmq 是 header-only”不等于“项目不需要 libzmq”。编译时要找到 `zmq.hpp`，链接和运行时仍需要 `libzmq`。

### 3.2 五个必须掌握的术语

| 术语 | 含义 | 本周需要掌握的重点 |
| --- | --- | --- |
| Context | ZeroMQ 的运行环境和资源管理对象 | 通常一个进程创建一个，可被多个线程使用 |
| Socket | 具有通信模式的消息端点 | 普通 Socket 不应在多个业务线程间随意共享 |
| Message | 一条有边界的消息 | 使用 `zmq::message_t` 表示 |
| Endpoint | Socket 使用的地址字符串 | 例如 `tcp://*:5555` |
| Transport | Endpoint 地址所使用的传输方式 | 例如 TCP、IPC、进程内通信 |

### 3.3 Context 和 I/O 线程

```cpp
zmq::context_t ctx(1);
```

这里的 `1` 表示 Context 使用的 ZeroMQ I/O 线程数量，不是：

- 业务线程数量；
- 客户端数量；
- Socket 数量；
- 能够同时执行的请求数量。

I/O 线程负责底层网络 I/O 等工作。业务线程仍然由程序通过 `std::thread`、线程池或其他方式创建。学习阶段使用 `1` 个 I/O 线程足以运行本周实验；实际数量要根据连接数量、传输方式和负载评估。

Context 可以被多个线程使用，但这不代表一个 Socket 可以被多个线程同时操作。

### 3.4 Socket 的线程归属原则

建议遵守以下规则：

1. 一个进程通常创建一个共享 Context；
2. 每个普通 Socket 只由创建它的业务线程使用；
3. 如果多个线程需要通信，让每个线程拥有自己的 Socket；
4. 在线程之间使用 `inproc://` 传递消息，而不是直接共享 Socket；
5. 在所有使用该 Context 的线程结束后，再销毁 Context。

可以共享的是 Context，不是普通 Socket。ZeroMQ 的某些特殊对象有不同规则，但不要把这些例外推广到普通 Socket。

## 4. Endpoint、bind 和 connect

### 4.1 Endpoint 地址结构

常见 Endpoint 格式如下：

```text
<transport>://<address>
```

示例：

```text
tcp://*:5555
tcp://127.0.0.1:5555
ipc:///tmp/week1-zeromq
inproc://week1-thread
```

Endpoint 是 Socket 使用的地址，不是一定意义上的“服务器地址”。Socket 的具体角色由 Socket 类型（如 REQ、REP、PUB、SUB）决定。

### 4.2 bind 的职责

`bind` 把 Socket 放到一个本地 Endpoint 上，等待其他 Socket 连接：

```cpp
zmq::socket_t sock(ctx, ZMQ_REP);
sock.bind("tcp://*:5555");
```

`*` 表示监听本机可用网卡上的地址。学习和本机实验可以使用它；生产环境应根据安全和网络规划限制监听地址。

### 4.3 connect 的职责

`connect` 让 Socket 连接到一个 Endpoint：

```cpp
zmq::socket_t sock(ctx, ZMQ_REQ);
sock.connect("tcp://127.0.0.1:5555");
```

`connect` 返回并不等于业务消息已经被对端处理。ZeroMQ 可能在后台建立连接，Socket 的发送操作会进入队列。对于本周的 REQ/REP 示例，只需要先启动服务端，再启动客户端，便于观察流程。

### 4.4 bind 和 connect 的关系

本周可用下面这张图记忆：

```text
服务端进程                                      客户端进程
+------------------+                           +------------------+
| Context          |                           | Context          |
| REP Socket       |                           | REQ Socket       |
| bind             |                           | connect          |
| tcp://*:5555     | <------ TCP 连接 -------- | tcp://127.0.0.1:5555 |
+------------------+                           +------------------+
       recv(request)  <----- request -----  send(request)
       send(reply)    ----- reply ------->  recv(reply)
```

要点：

- `bind` 和 `connect` 是建立通信关系的两端，不是 `send` 和 `recv` 的替代品；
- 在一个连接关系中，通常一端 `bind`，另一端 `connect`；
- ZeroMQ 不强制“服务端必须 bind、客户端必须 connect”的命名，但这种组织方式最容易理解；
- 同一个 Endpoint 可以由一个 Socket 绑定、多个 Socket 连接，具体行为还受 Socket 类型影响；
- `REP` 必须先接收再发送，`REQ` 必须先发送再接收，这是模式状态机的约束。

## 5. 三种常见 Transport

### 5.1 `tcp://`

用途：跨进程通信，也可以跨主机通信。

```text
tcp://127.0.0.1:5555
```

特点：

- 适合不同进程和不同主机；
- 需要 IP 地址和端口；
- 受防火墙、端口占用和网络连通性影响；
- 本周 REQ/REP 使用此传输方式。

### 5.2 `ipc://`

用途：同一台主机上的不同进程通信。

```text
ipc:///tmp/week1-zeromq
```

特点：

- 不跨主机；
- 通常使用文件系统路径表示 Endpoint；
- 省去了 TCP 端口，但仍然需要处理路径权限和残留文件等问题；
- 具体可用性与操作系统和 libzmq 构建方式有关。

### 5.3 `inproc://`

用途：同一进程内的线程之间通信。

```text
inproc://week1-thread
```

必须记住：

- 不能用于两个独立进程；
- 通信双方通常必须使用同一个 Context；
- 推荐先 `bind` 再 `connect`，再开始收发；
- 每个线程仍然应该使用自己的 Socket；
- `inproc://` 不代表可以直接共享 Socket，它仍然是消息传递。

三种传输方式对比：

| Transport | 通信范围 | 地址示例 | 典型用途 |
| --- | --- | --- | --- |
| TCP | 同机或跨主机 | `tcp://127.0.0.1:5555` | 服务进程之间通信 |
| IPC | 同一主机的不同进程 | `ipc:///tmp/app.sock` | 本机服务之间通信 |
| inproc | 同一进程的不同线程 | `inproc://worker` | 主线程和工作线程通信 |

### 7.4 按执行顺序阅读服务端

服务端的核心代码可以简化为：

```cpp
zmq::context_t ctx(1);
zmq::socket_t sock(ctx, ZMQ_REP);
sock.bind("tcp://*:5555");

while (true) {
    zmq::message_t request;
    auto result = sock.recv(request, zmq::recv_flags::none);
    if (!result) {
        break;
    }

    std::string text(static_cast<char*>(request.data()), request.size());
    std::string reply_text = "Hello " + text;
    zmq::message_t reply(reply_text.data(), reply_text.size());
    sock.send(reply, zmq::send_flags::none);
}
```

逐步理解：

1. 创建 Context；
2. 创建 REP Socket；
3. 绑定 TCP Endpoint；
4. 阻塞等待请求；
5. 读取消息内容；
6. 构造应答；
7. 发送应答；
8. 回到下一轮接收。

### 7.5 按执行顺序阅读客户端

客户端的核心流程是：

```cpp
zmq::context_t ctx(1);
zmq::socket_t sock(ctx, ZMQ_REQ);
sock.connect("tcp://localhost:5555");

zmq::message_t request("World", 5);
sock.send(request, zmq::send_flags::none);

zmq::message_t reply;
auto result = sock.recv(reply, zmq::recv_flags::none);
```

REQ/REP 的顺序不能随意调换：

```text
REQ: send -> recv -> send -> recv -> ...
REP: recv -> send -> recv -> send -> ...
```

如果让 REQ 连续发送两次，或者让 REP 连续接收两次，通常会违反该 Socket 类型的状态机约束。

### 7.6 验证动态库依赖

## 8. 第二个实验：`inproc://` 线程通信

这个实验验证三件事：

- Context 可以被多个线程使用；
- 每个线程可以使用自己的 Socket；
- `inproc://` 只在同一个进程内传递消息。

将下面内容保存为 `inproc_week1.cpp`：

```cpp
#include <iostream>
#include <string>
#include <thread>

#include <zmq.hpp>

void worker(zmq::context_t& ctx)
{
    // 这个 Socket 只属于 worker 线程。
    zmq::socket_t receiver(ctx, ZMQ_PAIR);
    receiver.connect("inproc://week1-thread");

    zmq::message_t message;
    auto result = receiver.recv(message, zmq::recv_flags::none);
    if (result) {
        std::string text(static_cast<char*>(message.data()), message.size());
        std::cout << "worker received: " << text << std::endl;
    }
}

int main()
{
    zmq::context_t ctx(1);

    // 这个 Socket 只属于 main 线程，并先 bind。
    zmq::socket_t sender(ctx, ZMQ_PAIR);
    sender.bind("inproc://week1-thread");

    std::thread thread(worker, std::ref(ctx));

    zmq::message_t message("hello worker", 12);
    sender.send(message, zmq::send_flags::none);

    thread.join();
    return 0;
}
```

如果使用当前项目的头文件和库，可以从 `test_zeromq` 目录执行：

```bash
g++ -std=c++11 -pthread \
  -I../cmake_libzmq/include \
  -I../cppzmq-4.11.0 \
  inproc_week1.cpp \
  -L../cmake_libzmq/lib -Wl,-rpath,'$ORIGIN/../cmake_libzmq/lib' \
  -lzmq -o inproc_week1
./inproc_week1
```

如果把源文件放在其他目录，请相应调整 `-I` 和 `-L` 路径。预期输出：

```text
worker received: hello worker
```

### 实验观察记录

按下面的问题记录结果：

1. `ctx` 是不是复制了一份给 worker？
2. `sender` 和 `receiver` 是否是同一个 Socket？
3. 如果把 Endpoint 改成 `tcp://127.0.0.1:5556`，它还属于 `inproc` 实验吗？
4. 如果在两个独立进程中分别使用 `inproc://week1-thread`，能否通信？
5. 如果不调用 `thread.join()` 就退出，程序生命周期是否安全？

正确方向：Context 由两个线程共享，Socket 各自归属一个线程；改成 TCP 后就是 TCP 实验；两个进程不能通过 `inproc://` 通信；线程必须结束后再销毁 Context。

## 9. cppzmq 的基本使用方式

### 9.1 常用类型

| cppzmq 类型 | 作用 |
| --- | --- |
| `zmq::context_t` | Context 的 RAII 封装 |
| `zmq::socket_t` | Socket 的 RAII 封装 |
| `zmq::message_t` | 消息对象 |
| `zmq::send_flags` | 发送选项 |
| `zmq::recv_flags` | 接收选项 |
| `zmq::error_t` | ZeroMQ 异常类型 |

cppzmq 是 header-only C++ binding，常见好处是：

- C API 中的句柄被映射为 C++ 类型；
- 对象离开作用域时自动释放资源；
- 错误可以通过异常和返回值处理；
- 可以使用 C++ 的字符串、容器和线程工具。

但它仍然依赖 libzmq：

```text
#include <zmq.hpp>       # 编译期需要 cppzmq 头文件
-lzmq                    # 链接期需要 libzmq
libzmq.so                # 运行期需要动态库
```

### 9.2 消息大小和字符串

`zmq::message_t` 是一段带长度的消息，不要求以 `\0` 结尾。因此接收后应使用消息长度构造字符串：

```cpp
std::string text(
    static_cast<char*>(message.data()),
    message.size());
```

不要默认把 `message.data()` 当成 C 字符串直接传给只接受 `\0` 结尾字符串的函数。

### 9.3 阻塞和非阻塞

本周使用：

```cpp
sock.send(message, zmq::send_flags::none);
sock.recv(message, zmq::recv_flags::none);
```

`none` 表示按默认行为执行，接收通常会等待消息。后续学习 `dontwait`、轮询、超时和高水位时，再处理非阻塞行为。

### 9.4 资源生命周期

推荐让 Context 和 Socket 通过作用域自动释放：

```cpp
int main()
{
    zmq::context_t ctx(1);
    zmq::socket_t sock(ctx, ZMQ_REQ);
    // 使用 sock
} // sock 和 ctx 自动清理
```

线程场景下要特别注意：先让工作线程结束，再让 Context 离开作用域。

## 10. 常见问题排查

### 10.1 `Address already in use`

原因通常是：

- 上一次服务端还在运行；
- 其他程序占用了 5555 端口；
- 程序异常退出后仍有进程占用端口。

排查：

```bash
ss -ltnp | rg ':5555'
ps -ef | rg 'build/service|test_zeromq'
```

结束确认过的旧进程，或者把服务端和客户端端口一起改成另一个未占用端口。

### 10.2 客户端一直等待

按以下顺序检查：

1. 服务端是否已经启动；
2. 两边端口是否一致；
3. 服务端是否绑定了 `*:5555`；
4. 客户端是否连接了 `localhost:5555`；
5. 是否把 REQ/REP 的 send/recv 顺序写反；
6. 是否启动了旧的二进制文件。

### 10.3 `zmq.hpp: No such file or directory`

这是编译期找不到 cppzmq 头文件：

```bash
ls /home/zhuzhonghua/zzh/github/ks_tree/zmq/test_zeromq/include/zmq.hpp
ls /home/zhuzhonghua/zzh/github/ks_tree/zmq/cppzmq-4.11.0/zmq.hpp
```

根据实际头文件所在位置补充 `-I`，或者检查 CMake 的 `include_directories`。

### 10.4 `cannot find -lzmq`

这是链接期找不到 libzmq：

```bash
ls /home/zhuzhonghua/zzh/github/ks_tree/zmq/cmake_libzmq/lib/libzmq.so*
```

确认编译命令包含正确的 `-L`，并且库名是 `libzmq.so` 或可被链接器识别的符号链接。

### 10.5 运行时 `libzmq.so... cannot open shared object file`

这是运行期动态链接器找不到库，不是编译失败。先使用本地临时环境变量验证：

```bash
export LD_LIBRARY_PATH=/home/zhuzhonghua/zzh/github/ks_tree/zmq/cmake_libzmq/lib:$LD_LIBRARY_PATH
```

再结合 `ldd build/client` 检查具体缺失项。

### 10.6 为什么不建议多个线程共享一个 Socket

普通 Socket 内部有状态机和队列，多个业务线程同时调用会造成并发访问和状态顺序问题。正确做法是：

```text
线程 A -- Socket A -- inproc://worker-a -- Socket B -- 线程 B
```

而不是：

```text
线程 A ---+
          +--- 同一个普通 Socket
线程 B ---+
```

## 12. 本周验收题与参考答案

### 题目

1. ZeroMQ 默认是否提供磁盘持久化？
2. `ctx(1)` 中的 `1` 是什么？
3. `bind` 和 `connect` 的职责分别是什么？
4. `tcp://` 与 `inproc://` 的边界是什么？
5. 一个普通 Socket 是否可以让多个业务线程随意共享？
6. cppzmq 是不是不需要链接 libzmq？
7. REQ/REP 的基本发送接收顺序是什么？
8. 当前工程编译后，服务端和客户端的可执行文件叫什么？

### 参考答案

1. **不是。** ZeroMQ 默认是进程内通信库，不自动提供消息磁盘持久化、崩溃恢复或消息中心服务。
2. **Context 的 ZeroMQ I/O 线程数量。** 它不是业务线程数量。
3. **`bind` 把 Socket 放到本地 Endpoint 上等待连接；`connect` 让 Socket 连接到某个 Endpoint。** 两者共同建立通信关系。
4. **`tcp://` 可用于同机或跨主机的进程通信；`inproc://` 只用于同一进程内的线程通信，通常需要共享同一个 Context。**
5. **不可以随意共享。** 普通 Socket 应遵守一个 Socket 一个业务线程的归属原则。
6. **不是。** cppzmq 是 header-only 的 C++ 封装，但编译和运行仍需要 libzmq 的头文件、库文件和运行时依赖。
7. **REQ：`send -> recv`；REP：`recv -> send`。** 两者交替执行。
8. **`build/service` 和 `build/client`。** 它们分别由 `service_rep.cpp` 和 `client_req.cpp` 构建。
