# 第 3 周学习资料：消息帧、多段消息与序列化

## 1. 学习目标

本周要建立“消息有边界、协议有结构、业务有校验”的认识。完成后能够：

- 区分单帧消息和 multipart 消息；
- 使用 `sndmore` 发送多帧，使用 `RCVMORE` 或 `recv_multipart` 接收；
- 正确处理空帧、二进制 payload 和嵌入 `\0` 的数据；
- 设计包含版本、请求 ID、操作和载荷的简单应用层协议；
- 解释 multipart 不等于业务事务；
- 为协议增加字段校验、长度限制和版本兼容策略。

## 2. 消息、帧和 multipart

ZeroMQ 的消息不是 TCP 字节流。TCP 只保证字节顺序，不能告诉应用一次 `send` 对应一次 `recv`。ZeroMQ/ZMTP 在传输层恢复消息和 frame 边界。

```text
一条逻辑消息
+---------+---------+----------+---------+
| version | req_id  | operation| payload |
| frame 1 | frame 2 | frame 3  | frame 4 |
+---------+---------+----------+---------+
```

multipart 的多个 frame 一起构成一次逻辑消息，但它不提供数据库事务、业务回滚或 exactly-once。

## 3. 发送和接收规则

前三帧发送 `sndmore`，最后一帧不带该标志：

```cpp
sock.send(zmq::buffer("v1"), zmq::send_flags::sndmore);
sock.send(zmq::buffer("request-000001"), zmq::send_flags::sndmore);
sock.send(zmq::buffer("get_user"), zmq::send_flags::sndmore);
sock.send(zmq::buffer("{\"user_id\":1001}"), zmq::send_flags::none);
```

使用 `zmq::recv_multipart` 时：

```cpp
std::vector<zmq::message_t> frames;
auto count = zmq::recv_multipart(sock, std::back_inserter(frames));
if (!count || frames.size() != 4) {
    // 拒绝不符合协议的消息
}
```

如果使用底层 API，需要在每次接收后检查 `ZMQ_RCVMORE`，判断是否还有后续 frame。接收 multipart 时必须完整消费整条消息，否则后续处理可能从错误的 frame 开始。

参考示例：[multipart_messages.cpp](../../cppzmq-4.11.0/examples/multipart_messages.cpp)。

## 4. 推荐的四帧协议

### 请求

| 帧 | 字段 | 约束 |
| --- | --- | --- |
| 1 | `version` | 例如 `v1`，不能为空 |
| 2 | `request_id` | 全局或客户端范围内唯一 |
| 3 | `operation` | 只允许已注册操作名 |
| 4 | `payload` | 按操作定义解析，并限制大小 |

示例：

```text
v1
request-000001
get_user
{"user_id":1001}
```

### 响应

可以使用同样的前两帧，并将第三、四帧定义为状态和结果：

```text
v1
request-000001
OK
{"user_id":1001,"name":"Alice"}
```

错误响应应包含稳定的错误码，而不是只返回自由文本：

```text
v1
request-000001
INVALID_ARGUMENT
user_id must be positive
```

## 5. 二进制和空帧

`zmq::message_t` 保存字节和长度，不要求以 `\0` 结尾：

```cpp
std::string payload("A\0B", 3);
zmq::message_t frame(payload.data(), payload.size());
```

接收时使用：

```cpp
std::string value(static_cast<char*>(frame.data()), frame.size());
```

空 frame 也可以合法存在，但必须在协议中明确含义。不要把“空帧”和“缺少帧”混为一谈：前者是存在但长度为 0，后者是 frame 数量不够。

## 6. 序列化格式如何选择

| 格式 | 优点 | 代价 | 学习阶段建议 |
| --- | --- | --- | --- |
| JSON | 可读、调试方便、生态广 | 体积较大，类型约束弱 | 先用它描述协议 |
| MessagePack | 二进制、比 JSON 紧凑 | 需要额外库，调试不如 JSON | 需要效率时考虑 |
| Protobuf | schema 明确、兼容性好 | 需要生成代码和工具链 | 生产 RPC 常用 |
| FlatBuffers | 可减少解析拷贝 | schema 和使用方式更复杂 | 对性能有明确需求时使用 |

序列化格式不能替代协议设计。仍然需要版本、长度、字段校验、错误码和兼容策略。

## 8. 常见错误

- 只接收第一帧就开始解析业务；
- 忘记最后一帧不带 `sndmore`；
- 把空 frame 当作消息结束；
- 把 payload 当作 C 字符串；
- 认为 multipart 自动保证业务原子性；
- 只校验 frame 数量，不校验版本、操作名和 payload 长度；
- 协议升级时直接删除旧字段，导致旧客户端无法工作。

建议使用“向后兼容地增加字段”，并为不支持的版本返回明确错误。

## 9. 本周练习与验收

回答以下问题：

1. 为什么 TCP 本身不能保证应用层消息边界？
2. 多帧发送如何标记最后一帧？
3. 如何判断还有没有后续 frame？
4. 空 frame 和缺少 frame 有什么区别？
5. multipart 是否自动提供业务事务？
6. 为什么 `message_t` 不能默认当 C 字符串？
7. 协议版本字段应该解决什么问题？

参考答案：ZeroMQ/ZMTP 负责消息和 frame 边界；前三帧使用 `sndmore`、最后一帧不使用；可检查 `RCVMORE` 或使用 `recv_multipart` 返回的 frame 数；空 frame 是存在的零长度 frame，缺少 frame 是协议结构不完整；multipart 不提供事务；消息是带长度的任意字节；版本字段用于兼容和演进。
