# 第 4 周学习资料：通信模式与拓扑

> 本资料配套计划：[第 4 周：通信模式和拓扑](第04周-通信模式与拓扑.md)。

## 1. 学习目标

本周不只是记住 Socket 名称，而是根据消息流向、并发方式、可靠性要求和拓扑规模选择模式。完成后能够：

- 画出 REQ/REP、PUSH/PULL、PUB/SUB、DEALER/ROUTER 的消息流；
- 说清楚每种模式的状态约束和常见误用；
- 编译并运行仓库中的模式示例；
- 选择适合查询、任务分发、广播和异步路由的模式；
- 解释 PUB/SUB 的订阅丢失风险，以及 ROUTER/DEALER 的 identity 和 envelope。

## 2. Socket 类型总览

| 模式 | 消息方向 | 常见用途 | 重要边界 |
| --- | --- | --- | --- |
| REQ/REP | 一问一答 | 简单同步 RPC | REQ、REP 都有严格交替状态 |
| PUSH/PULL | PUSH 到一个 PULL | 任务分发、流水线 | 无直接响应通道 |
| PUB/SUB | 一对多广播 | 事件、配置、行情 | 订阅前和慢订阅者可能丢消息 |
| DEALER/ROUTER | 双向异步 | 并发 RPC、网关、工作池 | 应用自己管理请求匹配和路由 |
| XPUB/XSUB | 发布订阅代理 | 订阅转发和桥接 | 适合构建代理 |
| PAIR | 一对一双向 | 控制通道 | 不适合作为通用多方模式 |

选择模式前先回答：消息是否需要响应？是否广播？是否允许多个未完成请求？是否需要独立路由？

## 3. REQ/REP：同步 RPC

```text
REQ --request--> REP
REQ <--reply---- REP
```

适合：查询用户信息、简单配置读取、短事务请求。REQ 必须 `send -> recv`，REP 必须 `recv -> send`。

不适合：

- 一个客户端并发等待大量响应；
- 服务端需要异步回调；
- 复杂网关路由；
- 需要在请求超时后保留多个未完成请求。

基线代码：[service_rep.cpp](../../test_zeromq/service_rep.cpp)、[client_req.cpp](../../test_zeromq/client_req.cpp)。

## 4. PUSH/PULL：任务分发

```text
PUSH --> PULL worker 1
     --> PULL worker 2
     --> PULL worker 3
```

PUSH 把消息分发给下游 PULL。多个 worker 时可以形成负载分配，适合图片处理、后台任务和流水线阶段。

限制：PULL 不会自动返回业务结果；如果需要结果，应另建结果通道，或改用 ROUTER/DEALER。慢消费者会形成背压，具体行为还受 HWM 和传输队列影响。

示例：[service_push.cpp](../../test_zeromq/service_push.cpp)、[client_pull.cpp](../../test_zeromq/client_pull.cpp)。更完整的任务流水线见 `zguide/examples/C++/taskvent.cpp`、`taskwork.cpp`、`tasksink.cpp`。

## 5. PUB/SUB：广播和主题过滤

```text
PUB --topic A--> SUB A
    --topic B--> SUB B
```

SUB 必须设置订阅过滤器，例如：

```cpp
subscriber.set(zmq::sockopt::subscribe, "weather");
```

PUB 不等待每个订阅者的确认，因此：

- SUB 建立订阅前发送的消息可能丢失；
- 慢订阅者可能受队列和 HWM 影响；
- PUB/SUB 不适合直接承担可靠任务队列；
- 重要事件通常需要快照、序号、持久化日志或重新同步机制。

示例：[service_pub.cpp](../../test_zeromq/service_pub.cpp)、[client_sub.cpp](../../test_zeromq/client_sub.cpp)。实验时先启动 SUB，再启动 PUB，并比较启动顺序带来的差异。

## 6. DEALER/ROUTER：异步和路由

```text
client DEALER --> ROUTER gateway --> worker DEALER
client DEALER <-- ROUTER gateway <-- worker DEALER
```

DEALER 没有 REQ/REP 的严格状态机，可以发送多个未完成请求。ROUTER 能看到并使用对端 identity，因此可以把响应路由回指定客户端。

使用 ROUTER 时要理解 envelope。常见消息结构类似：

```text
[client identity][empty delimiter][application frames...]
```

具体 envelope 取决于连接的对端 Socket 类型。不能把 identity frame 当成业务 payload，也不能把 ROUTER 当作普通 REP 使用。

仓库示例：[service_router.cpp](../../test_zeromq/service_router.cpp)、[client_dealer.cpp](../../test_zeromq/client_dealer.cpp)。完整工作池见 `zguide/examples/C++/rrbroker.cpp`、`rrclient.cpp`、`rrworker.cpp`。

## 8. 拓扑选择练习

| 需求 | 推荐模式 | 选择理由 |
| --- | --- | --- |
| 查询用户信息 | REQ/REP | 简单同步一问一答 |
| 多 worker 处理无返回任务 | PUSH/PULL | 天然任务分发 |
| 广播配置变化 | PUB/SUB | 一对多主题广播 |
| 客户端独立路由 | ROUTER/DEALER | 可以使用 identity 路由 |
| 主线程和 worker 控制 | PAIR + `inproc://` | 同进程一对一控制 |
| 多请求并发 RPC | DEALER/ROUTER | 应用自行匹配 request ID |

不要只根据“客户端/服务端”命名选择 Socket。先画消息方向和是否需要响应。

## 9. 实践实验

### 实验一：PUB/SUB 启动顺序

分别执行：

1. 先启动 PUB，延迟几秒再启动 SUB；
2. 先启动 SUB，再启动 PUB；
3. 修改主题过滤器，观察不匹配主题；
4. 让 SUB 暂停读取，观察消息和队列行为。

结论应记录“消息可能丢失”而不是简单写“PUB 不可靠”。具体可靠性取决于是否有快照、序号和重放设计。

### 实验二：PUSH/PULL 多 worker

启动一个 PUSH 和多个 PULL，给每个 worker 打印自己的名字，观察任务如何分配。让一个 worker 睡眠更久，比较任务分布和背压。

### 实验三：ROUTER/DEALER 并发

让 DEALER 连续发出多个带 request ID 的请求，ROUTER 根据 identity 和 request ID 返回。记录：

- identity frame；
- delimiter frame；
- 业务 frame；
- 响应匹配依据。

## 10. 常见误区

- 用 PUB/SUB 做必须不丢的任务队列；
- 用 PUSH/PULL 期待自动返回任务结果；
- 以为 DEALER 会自动匹配响应；
- 忽略 ROUTER 的 identity 和 envelope；
- 以为所有 Socket 都遵循 REQ/REP 的收发顺序；
- 以为多 worker 就自动实现了业务幂等和重试；
- 只看吞吐量，不考虑背压、消息丢失和故障恢复。
