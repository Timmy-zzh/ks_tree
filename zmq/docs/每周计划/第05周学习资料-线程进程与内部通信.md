# 第 5 周学习资料：线程、进程与内部通信

> 本资料配套计划：[第 5 周：线程、进程和内部通信](第05周-线程进程与内部通信.md)。

## 1. 学习目标

完成本周后能够：

- 区分业务线程、ZeroMQ I/O 线程和进程；
- 正确共享 Context，避免跨线程共享普通 Socket；
- 使用 `inproc://` 连接同一进程内的 worker；
- 区分 `inproc://`、`ipc://` 和 `tcp://` 的边界；
- 说明 fork 后为什么不能直接复用父进程中的 Context 和 Socket；
- 画出主线程、代理和 worker 的生命周期图。

## 2. 三个层次

```text
进程
+------------------------------------------------+
| 业务线程 A       业务线程 B       ZeroMQ I/O 线程 |
|   Socket A         Socket B          底层 I/O     |
|       \             /                 |          |
|             共享 Context              |          |
+------------------------------------------------+
```

- **进程**：操作系统资源边界。`inproc://` 不能跨进程。
- **业务线程**：执行应用逻辑。普通 Socket 应归属单一业务线程。
- **I/O 线程**：由 Context 管理，处理底层通信工作，不等同于业务 worker。

Context 可以被多个线程使用，但 Socket 的线程安全规则不同：不要把同一个普通 Socket 同时交给多个业务线程。

## 3. 推荐架构

```text
主线程 ROUTER
      |
      | inproc://backend
      v
内部 DEALER
      |
      +--> worker 1（Socket 1）
      +--> worker 2（Socket 2）
      +--> worker 3（Socket 3）
```

主线程和每个 worker 共享一个 Context，但每个线程创建、使用和关闭自己的 Socket。线程之间通过消息通信，而不是通过共享 Socket 对象。

## 4. 三种传输范围

| Transport | 范围 | 是否跨进程 | 是否跨主机 |
| --- | --- | --- | --- |
| `inproc://` | 同一进程线程 | 否 | 否 |
| `ipc://` | 同一主机进程 | 是 | 否 |
| `tcp://` | 进程或主机 | 是 | 是 |

`inproc://` 通常要求通信双方使用同一个 Context。推荐先 bind，再启动线程并 connect，避免早期版本或特定实现下的连接时序问题。

## 5. 最小线程实验

可以使用第 1 周的 `inproc` 示例，或参考：

- `cppzmq-4.11.0/examples/pubsub_multithread_inproc.cpp`
- `zguide/examples/C++/mtserver.cpp`
- `zguide/articles/multithreading.md`

核心结构：

```cpp
void worker(zmq::context_t& ctx)
{
    zmq::socket_t worker_socket(ctx, ZMQ_PAIR);
    worker_socket.connect("inproc://worker");
    // 只在 worker 线程使用 worker_socket
}

int main()
{
    zmq::context_t ctx(1);
    zmq::socket_t main_socket(ctx, ZMQ_PAIR);
    main_socket.bind("inproc://worker");

    std::thread thread(worker, std::ref(ctx));
    main_socket.send(zmq::buffer("work"), zmq::send_flags::none);
    thread.join();
}
```

关键不是 `PAIR` 本身，而是 Context 共享、Socket 独占和线程先后顺序。

## 6. worker pool 实验

将架构扩展为：

1. 主线程创建前端 ROUTER；
2. 主线程或代理创建后端 DEALER；
3. 后端通过 `inproc://backend` 连接多个 worker；
4. 每个 worker 在自己的线程中创建 DEALER 或 REP；
5. 每个 worker 处理任务并回传结果；
6. 主线程在停止时先通知 worker，再等待线程结束。

可参考 `zguide/examples/C++/rrbroker.cpp`、`rrworker.cpp` 和 `rrclient.cpp`。学习时先用 `inproc`，再尝试将后端改为 `ipc` 或 `tcp`，比较边界变化。

## 7. 错误架构与正确架构

错误：

```text
线程 A ---+
          +--- 同一个普通 Socket
线程 B ---+
```

正确：

```text
线程 A -- Socket A -- inproc://control -- Socket B -- 线程 B
```

错误架构可能出现竞态、状态机顺序错误、关闭时崩溃或难以复现的消息问题。线程安全队列也可以作为业务层的替代方案，但不能因此把普通 Socket 当成线程安全对象。

## 8. fork 注意事项

如果使用 `fork()`：

- 不要在 fork 前创建并在子进程继续复用 Context 或 Socket；
- 子进程应根据自身职责重新创建 Context 和 Socket；
- 更推荐使用明确的进程启动方式和 `ipc://`/`tcp://` 通信；
- 进程退出时要处理 Socket 的 `LINGER` 和 Context 终止。

参考测试：`libzmq-4.3.5/tests/test_fork.cpp`、`test_thread_safe.cpp`。

## 10. 生命周期和关闭顺序

推荐关闭顺序：

```text
停止接收新任务
  -> 通知 worker 停止
  -> worker 完成或取消任务
  -> join 所有业务线程
  -> 关闭各线程 Socket
  -> Context 退出
```

不要在线程仍使用 Context 时让主线程销毁 Context。也不要依赖进程立即退出来掩盖未完成的 Socket 生命周期问题。
