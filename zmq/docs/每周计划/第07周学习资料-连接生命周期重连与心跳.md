# 第 7 周学习资料：连接生命周期、重连与心跳

> 本资料配套计划：[第 7 周：连接生命周期、重连和心跳](第07周-连接生命周期重连与心跳.md)。

## 1. 学习目标

本周要理解连接从创建到关闭的完整生命周期，掌握自动重连和心跳的边界。完成后能够：

- 区分 `bind`、`connect` 返回与真正建立连接；
- 解释客户端先启动、服务端先启动和对端重启的差异；
- 配置重连间隔、握手超时和心跳；
- 说明自动重连不等于业务消息自动恢复；
- 通过事件日志和请求结果定位断线问题。

## 2. 连接生命周期

```text
Socket 创建
  -> connect/bind
  -> connect_delayed 或连接尝试
  -> TCP 建立
  -> ZMTP 握手
  -> connected/accepted
  -> 业务收发
  -> disconnected
  -> reconnecting
```

`connect()` 调用返回通常只表示连接请求已提交。服务端尚未启动时，客户端可以保持 Socket 存活并后台重试，而不是立刻把“对端不可达”作为同步异常抛出。

## 3. 重要参数

| 参数 | 作用 |
| --- | --- |
| `ZMQ_RECONNECT_IVL` | 初始重连间隔，负值表示禁用自动重连 |
| `ZMQ_RECONNECT_IVL_MAX` | 指数退避时的最大间隔 |
| `ZMQ_HANDSHAKE_IVL` | ZMTP 握手等待上限 |
| `ZMQ_HEARTBEAT_IVL` | 心跳发送间隔 |
| `ZMQ_HEARTBEAT_TIMEOUT` | 心跳超时时间 |

参数需要结合业务请求超时设置。心跳只说明底层连接仍有响应，不代表业务线程没有卡死，也不代表请求一定能成功。

## 4. 启动顺序实验

实验 A：先启动服务端，再启动客户端。记录 bind、connect、第一条请求的时间。

实验 B：先启动客户端，再启动服务端。观察客户端是否立即报错，服务端启动后请求是否可以成功。

实验 C：运行期间停止服务端，再重新启动。记录：

- 最后一条成功请求；
- 断开时间；
- 重连时间；
- 重连期间发送的消息；
- 服务端恢复后的第一条请求。

不要默认认为重连期间排队的消息一定被处理。消息可能因为 Socket 关闭、队列限制、`LINGER` 或应用重试策略而丢失或重复。

## 5. 配置示例

```cpp
zmq::socket_t sock(ctx, ZMQ_DEALER);
sock.set(zmq::sockopt::reconnect_ivl, 100);
sock.set(zmq::sockopt::reconnect_ivl_max, 2000);
sock.set(zmq::sockopt::handshake_ivl, 3000);
sock.set(zmq::sockopt::heartbeat_ivl, 1000);
sock.set(zmq::sockopt::heartbeat_timeout, 3000);
sock.connect("tcp://127.0.0.1:5555");
```

先用较小的实验参数观察行为，生产环境需要根据网络延迟和服务恢复时间评估，避免所有客户端同时重连形成重连风暴。随机抖动、限速和连接分组都可以缓解该问题。

## 7. 常见误区

- `connect()` 返回就认为业务可用；
- 自动重连就等于请求自动重试；
- 心跳成功就认为业务处理线程健康；
- 重连期间的本地消息一定不会丢；
- 所有客户端使用同一重连间隔不会造成风暴；
- TCP 断开后立即知道对端已经崩溃。

应把健康拆成三层：进程健康、连接健康、业务健康。

## 8. 本周验收

回答：

1. 客户端连接失败时是否一定立即报错？
2. 服务端重启后 Socket 是否可能自动恢复？
3. 重连期间消息是否一定保留？
4. 心跳检测的是连接存活还是业务可用？
5. 如何避免重连风暴？

参考结论：连接失败可能由后台机制处理；Socket 可能自动恢复底层连接；消息保留取决于队列、关闭和应用策略；心跳主要检测连接层；应使用退避、抖动和限速。
