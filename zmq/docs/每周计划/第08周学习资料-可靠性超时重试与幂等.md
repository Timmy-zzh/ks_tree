# 第 8 周学习资料：可靠性、超时、重试与幂等

> 本资料配套计划：[第 8 周：业务可靠性、超时、重试和幂等](第08周-可靠性超时重试与幂等.md)。

## 1. 学习目标

ZeroMQ 负责通信，不会自动替业务实现事务和 exactly-once。本周要从端到端角度设计超时、重试、请求标识和幂等。

完成后能够：

- 设置合理的请求超时和有限重试；
- 使用指数退避和随机抖动；
- 用 request ID 区分重复请求；
- 处理“业务成功但响应丢失”；
- 用去重表、唯一约束或状态查询避免重复执行；
- 解释 at-most-once、at-least-once 和 exactly-once 的边界。

## 2. 关键故障场景

```text
客户端发送 request_id=1001
  -> 服务端收到
  -> 服务端完成数据库更新
  -> 服务端在发送响应前崩溃
  -> 客户端超时
  -> 客户端重试 request_id=1001
  -> 服务端再次收到相同请求
```

如果服务端直接重复执行，业务可能被扣款两次、创建两条订单或重复发送通知。传输层重试不能自动解决业务重复。

## 3. 一次请求的状态机

```text
NEW
  -> SENT
  -> WAITING
  -> SUCCESS
       |
       +-> TIMEOUT -> BACKOFF -> RETRYING
                              |
                              +-> 超过上限 -> UNKNOWN/FAILED
```

`UNKNOWN` 很重要：客户端超时并不证明服务端没有执行。对于写操作，应优先查询状态，而不是无条件再执行。

## 4. 请求协议

最小请求字段：

```text
version | request_id | operation | payload
```

响应字段：

```text
version | request_id | status | result_or_error
```

request ID 应由客户端生成，服务端在日志、去重表和响应中原样保留。不要只用时间戳；并发客户端可能产生冲突。

## 5. 超时、退避和重试

伪代码：

```text
for attempt in 0..max_retries:
    send(request_id)
    if receive_with_timeout(response):
        return response
    sleep(base * 2^attempt + random_jitter)
return UNKNOWN
```

建议：

- 设置最大重试次数；
- 设置总截止时间；
- 只对可重试错误重试；
- 为退避增加随机抖动；
- 将 request ID 固定在整个重试周期内；
- 读操作和写操作使用不同策略；
- 记录每一次尝试和最终状态。

## 6. 幂等和去重

服务端收到请求后：

1. 校验 request ID 和参数；
2. 查询去重记录；
3. 如果已完成，返回历史结果；
4. 如果处理中，返回处理中状态或等待；
5. 如果不存在，在业务事务中写入处理记录并执行；
6. 保存结果；
7. 发送响应。

可选实现：

- 内存去重表：简单但重启丢失；
- 数据库唯一约束：可靠，但需要业务事务；
- Redis 等外部存储：适合分布式，但需要处理过期和一致性；
- 业务天然幂等：例如设置状态为某个值，而不是累加一次。

## 8. 可靠性语义

- **At-most-once**：最多执行一次，可能丢失；
- **At-least-once**：尽量保证执行，但可能重复；
- **Exactly-once**：需要端到端业务约束，不能仅靠 ZeroMQ 的发送和接收 API 宣称实现。

生产 RPC 常使用“至少一次传输 + request ID 去重 + 状态查询”，而不是声称底层自动 exactly-once。

## 9. 本周验收

必须能够说明：

- ZeroMQ 可以传输消息；
- ZeroMQ 不会自动实现 ACK、事务、幂等和 exactly-once；
- 超时后的响应可能已经在服务端产生；
- 重试必须携带同一个 request ID；
- 写操作必须设计重复执行保护。
