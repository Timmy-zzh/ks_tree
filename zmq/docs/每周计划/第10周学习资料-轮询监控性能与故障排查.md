## 2. poll 的基本思想

阻塞 `recv()` 只能等待一个 Socket。轮询可以让一个线程等待多个事件：

```text
poll
  +-- client socket readable -> recv request
  +-- control socket readable -> shutdown
  +-- monitor socket readable -> read connection event
```

cppzmq 的 poller 示例可参考 `cppzmq-4.11.0/tests/poller.cpp`；Guide 示例可参考 `zguide/examples/C++/mspoller.cpp`。

伪代码：

```cpp
while (!stopping) {
    // 等待一组 Socket 的输入事件
    poller.wait(events, std::chrono::milliseconds(100));
    if (client_has_input)
        handle_client();
    if (control_has_input)
        stopping = true;
}
```

轮询不是自动并发。一个事件处理太久，仍会阻塞同一线程上的其他 Socket，因此业务处理通常应转发给 worker。

## 3. Socket monitor

Socket monitor 用于观察连接生命周期，常见事件包括：

- `connect_delayed`；
- `connected`；
- `accepted`；
- `disconnected`；
- `accept_failed`；
- 握手成功或失败。

参考：

- `cppzmq-4.11.0/tests/monitor.cpp`
- `libzmq-4.3.5/tests/test_monitor.cpp`
- `libzmq-4.3.5/doc/zmq_socket_monitor.txt`

监控事件描述底层连接状态，不等于业务请求成功。需要把 monitor 事件与请求日志、超时和业务状态关联起来。

## 4. 指标定义

建议至少记录：

| 指标 | 含义 |
| --- | --- |
| request_total | 收到的请求数 |
| response_total | 发出的响应数 |
| business_success | 业务成功数 |
| business_error | 业务失败数 |
| recv_error/send_error | 收发错误数 |
| timeout_total | 超时数 |
| eagain_total | 非阻塞暂不可用次数 |
| retry_total | 重试数 |
| duplicate_total | 重复请求数 |
| connections | 当前连接数 |
| reconnect_total | 重连次数 |
| handshake_failed | 握手失败数 |
| latency | 请求到响应的耗时 |
| message_size | 消息大小分布 |

每个指标应有单位、标签、采集位置和告警阈值，不能只写一个没有定义的数字。

## 5. 延迟和吞吐量

吞吐量可以定义为：

```text
吞吐量 = 完成请求数 / 测量时间
```

延迟需要保存每个请求的耗时样本，再计算分位数：

- P50：一半请求不超过该延迟；
- P95：95% 请求不超过该延迟；
- P99：99% 请求不超过该延迟。

平均值可能掩盖少数极慢请求，生产服务应重点关注 P95/P99。

## 7. 故障排查流程

```text
请求失败
  -> 是连接事件异常吗？检查 monitor
  -> 是超时或 EAGAIN 吗？检查队列/HWM/消费者
  -> 是业务错误吗？检查请求参数和服务日志
  -> 是资源耗尽吗？检查 CPU、内存、FD、网络
  -> 是重试增加吗？检查对端重启和网络
```

排查时关联四类信息：请求 ID、时间戳、Socket/连接、业务结果。日志中不要只打印“失败”。
